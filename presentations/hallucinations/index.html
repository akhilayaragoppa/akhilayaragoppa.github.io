01 · What is a hallucination

A model saying something false — confidently.

Hallucination is when a language model generates content that's factually incorrect, inconsistent with the material it was actually given, or entirely fabricated — and states it with the same fluent confidence as something true. OpenAI's framing: "plausible yet incorrect statements," produced when a model is genuinely uncertain but answers as if it isn't.

Kalai, Nachum, Vempala & Zhang, "Why Language Models Hallucinate," OpenAI, Sept 2025 Anthropic — "Reduce hallucinations"

03 · Why does this happen

Two culprits — and they compound each other

Culprit one

The model hasn't seen enough

Facts that appear rarely in training data get learned unreliably — no matter how big the model is.

Culprit two

We're grading the wrong thing

Leaderboards reward confident guessing over honest uncertainty.

04 · Culprit one — the long tail

If it only appears once in training, the model is guessing

Kandpal et al. (ICML 2023) showed QA accuracy on a fact tracks directly with how many pretraining documents mention it. Rare facts stay unreliable — even in the biggest models.

Kandpal, Deng, Roberts, Wallace & Raffel, "Large Language Models Struggle to Learn Long-Tail Knowledge," ICML 2023
05 · Culprit two — the scoreboard

Every launch is covered as a leaderboard win

The pressure isn't just internal scoring rules — it's the press cycle. A launch gets measured by whether it beat the last leaderboard, not by whether it was careful.

New Atlas, Dec 6, 2023 PCWorld, Dec 13, 2023
06 · But is it actually getting better?

Yes. A massive difference.

Reason one

The metrics changed

Leaderboards are shifting from pure knowledge recall to task performance.

Reason two

The training changed

Labs are training directly against confident fabrication, not just measuring it after the fact.

Reason three

The numbers say so

Published hallucination rates are, for most models, trending down.

08 · Reason two — the training changed

Labs are training against the habit itself

OpenAI

Penalize confident wrong answers

Explicit credit for calibrated abstention, a real penalty for confident fabrication — built into how the model is scored, not just measured after training.

Anthropic

Honesty as a character trait

Neither claims victory. Anthropic's own model card: "Claude models still confabulate — getting facts wrong, hallucinating details, and filling gaps in knowledge with fabrication."

10 · The uncomfortable proof

Some hallucination is mathematically unavoidable

Xu, Jain & Kankanhalli, 2024

Computability argument

No LLM computes every computable function — used generally, it will hallucinate on some inputs, however it's trained.

Kalai & Vempala, STOC 2024

Calibration argument

A calibrated model has a provable hallucination-rate floor — roughly the share of facts appearing exactly once in training data, even on clean data.

11 · Case study — when no one was watching

Nobody asked it to. It deleted the database anyway.

A Cursor coding agent, running Claude Opus 4.6, hit a credential error on a routine task at PocketOS, a car-rental SaaS platform. It found an over-permissioned API token, decided on its own that wiping the production database would "fix" the problem — and took every backup stored on that same volume down with it.

12 · How to go from theory to production?

Assume it will fail. Build the system to catch it.

Detect → Mitigate
13 · Mitigate — prompt level (do this always)

The cheapest fixes are sentences, not systems

01

License "I don't know."

Without permission to be uncertain: "What page is that on?" → a confident, invented "p. 214."

"If you're not certain, say so — don't guess."
02

Ground every claim in the source.

Turns an invented statistic into a traceable one — or an honest "not in the source."

"Only answer from the document provided; cite the exact passage."
03

Add a self-check pass.

Catches a fabricated citation before it reaches the reader.

"Before answering, re-read your draft and flag anything you're not fully sure of."
14 · Mitigate — system & architecture level

Design the pipeline so fabrication has nowhere to hide

01

RAG — ground it in real documents.

Answer only from retrieved documents, not parametric memory.

Without it: "What's our refund policy?" → an invented policy. With it: cites the real doc.
02

Structured output + schema validation.

Constrain what the model can even output; reject malformed fields.

A free-text order ID can be fabricated. A schema requiring a real ID pattern rejects it.
03

A verifier checks the answer before it ships.

Ask twice and compare (self-consistency), or run a second "critic" pass.

Critic prompt: "Does this answer's claims match the source? Flag anything unsupported."
15 · Mitigate — process & organizational level

The last line of defense is a human who's actually looking

01

Human-in-the-loop, scaled to risk.

Not every output — just the ones that matter.

Flag medical, legal, or financial figures for review; low-stakes chat goes straight through.
02

Surface confidence, don't hide it.

Show uncertainty instead of hiding it.

"I'm fairly confident, but you may want to confirm this" beats false certainty about a wrong date.
03

Test and monitor continuously.

Not a one-time audit — a recurring practice.

Run a "trick question" eval set on every change; log flagged/corrected hallucinations in prod.
16 · Reference — the cascade, end to end

What "detect, then mitigate" looks like as a pipeline

hallucination_guard_pipeline.py Python · architectural pseudocode 
"""
Production hallucination detection + mitigation cascade.

This is architectural pseudocode, not a runnable library — it's meant to show
WHERE each real tool/model plugs in and WHY the pipeline is staged the way it
is (cost/latency control). Each function below names the concrete tool
choices teams actually reach for at that stage in 2026, and can be wired in
as:
  - a NeMo Guardrails output rail (Colang "flow" calling these as actions), or
  - a Guardrails AI custom Validator class, or
  - standalone middleware sitting between your generation call and the
    response you send to the user (framework-agnostic — this is the most
    common real-world setup, since the hallucination-specific logic below is
    usually custom-built even when NeMo/Guardrails AI handle everything else
    — auth, PII, topic rails, structured-output enforcement).

Overall shape: cheap gate -> fast classifier/NLI (runs on ~100% of eligible
traffic) -> expensive LLM judge (runs only on the borderline % that the fast
stage can't confidently resolve). This is the "cascade" pattern because
running an LLM judge on every claim of every response is what makes
hallucination detection too slow/expensive to ship.
"""

from dataclasses import dataclass


@dataclass
class Verdict:
    claim: str
    label: str          # "SUPPORTED" | "UNSUPPORTED" | "UNCERTAIN"
    source_chunk: str | None
    score: float
    stage: str           # which stage produced this verdict, for debugging/audit


def hallucination_guard(query, context_chunks, answer, trace_id):

    # ------------------------------------------------------------------
    # STAGE 0 — Fact-seeking gate
    # ------------------------------------------------------------------
    # Purpose: don't run expensive checks on traffic that doesn't need them.
    # "Write me a poem" or "summarize the tone of this email" isn't a
    # factual claim against your KB — skip straight through.
    #
    # Tooling: usually just a small classifier or even a rules/regex layer
    # on the query. HaluGate (vLLM's implementation) calls this the
    # "sentinel" model — a small, cheap model (can run on CPU) whose only
    # job is a binary FACT_CHECK_NEEDED / NO_FACT_CHECK_NEEDED call.
    # Doesn't need to be an LLM at all; a fine-tuned tiny classifier or even
    # intent-tagging is enough.
    if not is_fact_seeking(query):
        return PASS(answer)

    # ------------------------------------------------------------------
    # STAGE 1 — Claim decomposition
    # ------------------------------------------------------------------
    # Purpose: break the answer into atomic, independently-checkable
    # factual statements instead of scoring the whole answer as one blob.
    # This matters because an answer-level "faithfulness score" hides the
    # case where 9 sentences are correct and 1 fabricated citation is
    # buried in the middle — averaging washes that out.
    #
    # Tooling: typically a cheap/fast LLM call with a structured prompt
    # ("list each factual claim in this text as a standalone sentence"),
    # e.g. GPT-4o-mini / Claude Haiku / a small local model. Some teams use
    # a fine-tuned sentence-splitter + coreference resolution step instead
    # of a full LLM call to keep this stage cheap too.
    claims = decompose_into_claims(answer)

    results: list[Verdict] = []

    for claim in claims:

        # --------------------------------------------------------------
        # STAGE 2 — Fast NLI entailment check (runs on every claim)
        # --------------------------------------------------------------
        # Purpose: for each claim, check whether it's "entailed" by any of
        # the retrieved context chunks — i.e., treat it as a Natural
        # Language Inference problem: premise = retrieved chunk,
        # hypothesis = claim, label = entailment / contradiction / neutral.
        # This is the actual "groundedness" check and is what most
        # production systems run on ~100% of traffic, because it's a small
        # encoder model, not a generative LLM call — order of 200-500ms,
        # not 1-3s.
        #
        # Tooling options actually used for this:
        #   - Off-the-shelf NLI cross-encoders: e.g. cross-encoder/nli-deberta-v3-base,
        #     MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli
        #   - AlignScore (RoBERTa-based factual-consistency scorer) — this is
        #     what NeMo Guardrails' built-in fact-checking rail uses by default
        #   - Purpose-built hallucination encoders: Vectara's
        #     hallucination_evaluation_model, Bespoke-MiniCheck,
        #     KRLabs' LettuceDetect (ModernBERT-based, token-level)
        #   - Deepchecks' ORION / "Grounded in Context" — retrieval + NLI
        #     combined into one lightweight scorer, 512-token window
        best_chunk, nli_score = max(
            (chunk, nli_entail(premise=chunk, hypothesis=claim))
            for chunk in context_chunks
        )

        if nli_score > 0.9:
            results.append(Verdict(claim, "SUPPORTED", best_chunk, nli_score, stage="nli"))

        elif nli_score < 0.3:
            results.append(Verdict(claim, "UNSUPPORTED", None, nli_score, stage="nli"))

        else:
            # ----------------------------------------------------------
            # STAGE 3 — LLM judge (only for the borderline band, 0.3-0.9)
            # ----------------------------------------------------------
            # Purpose: the NLI model isn't confident either way — this is
            # where nuance, negation, numeric mismatches, or multi-hop
            # reasoning tend to confuse a small encoder. Escalate ONLY
            # these claims to something more expensive that can reason
            # about them in context.
            #
            # Tooling options:
            #   - A frontier LLM as judge with a faithfulness-style prompt
            #     (this is what RAGAS's "faithfulness" metric does under
            #     the hood — GPT-4o/Claude/etc. scoring claim vs. context)
            #   - Purpose-built hallucination-judge models instead of a
            #     general LLM: Patronus Lynx (8B/70B, what NeMo Guardrails
            #     ships as a pluggable rail), CleanLab TLM, Galileo Luna-2
            #   - Whichever you pick, this is the 1-3 second, real-money
            #     call — which is exactly why stages 0-2 exist, to keep
            #     this stage's volume small (5-20% of traffic in low-stakes
            #     settings, 100% in compliance-sensitive ones like clinical
            #     or legal claims, per current production writeups)
            judge_verdict = llm_judge_claim(claim, context_chunks)
            results.append(judge_verdict)

    # ------------------------------------------------------------------
    # Separate check: citation/provenance validity (not an NLI problem)
    # ------------------------------------------------------------------
    # Purpose: catch the specific failure where a claim IS attached to a
    # citation, but either (a) that chunk_id was never actually retrieved,
    # or (b) the cited chunk exists but doesn't actually contain the claim.
    # This is a structural lookup against your retrieval trace, not a
    # semantic-similarity problem — implement as a simple existence +
    # substring/embedding-overlap check against the chunk_ids your
    # retriever actually returned for this query.
    citation_issues = check_citation_provenance(answer, context_chunks)

    # ------------------------------------------------------------------
    # Logging / observability
    # ------------------------------------------------------------------
    # Purpose: every verdict (which stage produced it, score, chunk used)
    # gets written to a trace so you can audit false positives/negatives
    # later and track hallucination rate as a trend, not just gate live
    # traffic. Tooling: Arize Phoenix / LangSmith / Braintrust / an OTel
    # span with these as span attributes — whatever your tracing backend is.
    log_to_trace(trace_id, query, answer, results, citation_issues)

    unsupported = [r for r in results if r.label == "UNSUPPORTED"]

    # ------------------------------------------------------------------
    # MITIGATION — what actually happens once you've found a problem
    # ------------------------------------------------------------------
    if not unsupported and not citation_issues:
        return PASS(answer)

    if is_high_stakes(query):
        # e.g. clinical dosage claims, legal citations, claims-adjudication
        # numbers — don't auto-correct, put a human in the loop.
        # Tooling: push to a review queue/dashboard (this is the
        # "human-in-the-loop" layer that agentic frameworks like CHARM
        # wire into their governance stack), or a Slack/ticket alert.
        return ROUTE_TO_HUMAN_REVIEW(answer, unsupported, citation_issues)

    if len(unsupported) / max(len(claims), 1) < 0.2:
        # Most of the answer is fine — surgically remove/rewrite just the
        # bad span instead of throwing away a mostly-good answer.
        # Tooling: a small LLM rewrite call scoped only to the flagged
        # sentence(s), or template-based redaction if you'd rather not risk
        # introducing a new hallucination while "fixing" the old one.
        clean_answer = strip_or_rewrite_claims(answer, unsupported)
        return PASS(clean_answer, flagged=True)

    # Too much of the answer is ungrounded to salvage piecemeal —
    # regenerate from scratch with a stricter grounding constraint
    # (e.g. "answer only using the excerpts below, and cite the chunk_id
    # for every sentence"). This is also where NeMo's retrieval rails or
    # Guardrails AI's re-ask mechanism would trigger if you're using their
    # orchestration layer instead of custom middleware.
    regenerated = regenerate_with_grounding_constraint(query, context_chunks)
    return PASS(regenerated, regenerated_from=answer)
The end — or: where you come in

Models will keep guessing. Systems don't have to.

Detection plus layered mitigation is the actual job now: catch it before it reaches anyone, and stack enough checks that when one layer misses, the next one doesn't.
